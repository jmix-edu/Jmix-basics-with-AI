== Цель

Подключить аддон Jmix AI Tools: сотрудник и офис-менеджер задают в чате вопросы
о данных приложения («какие переговорки свободны на 3-м этаже», «мои брони на
завтра») и получают ответ от модели `z-ai/glm-5.2` через OpenRouter. Модель
видит ровно те данные, которые пользователь видит в приложении.

Только для разработки: профили, настройки прод-окружения, Docker Compose и
деплой — урок 4 (`04_deployment`).

== Что даёт аддон

Сведения сняты с исходников AI Tools 3.0.1–3.0.2 из кэша Gradle; проект
получит версию 3.0.3 из Jmix BOM. При реализации сверить с ней.

* *Экраны.* Хаб чатов `aitls_AiChatHubView` (маршрут `aitls/chats`, пункт
  меню в отдельной группе `aitls`) и чат `aitls_AiChatView`
  (`aitls/chat/:id?`). Тексты экранов на русском уже есть в
  `jmix-translations-ru`.
* *История чатов* хранится в БД: таблицы `AITLS_AI_CONVERSATION_ENTITY` и
  `AITLS_AI_CHAT_MESSAGE_ENTITY`, changelog поставляется аддоном. Каждый
  пользователь видит только свои разговоры: сервисы аддона фильтруют их по
  текущему пользователю.
* *Роль* `aitools-chat-user` (scope UI): доступ к экранам чата, пункту меню и
  сущностям разговоров.
* *Инструменты для модели (data load).* Модель видит описание сущностей
  приложения и может генерировать JPQL-запросы на чтение. Аддон выполняет их
  через обычный `DataManager.loadValues` от имени текущего пользователя:
  проверяет право чтения сущности и выкидывает колонки, на которые у
  пользователя нет прав. Запросы только на чтение, не больше 100 строк.
* *Модель* аддон берёт из Spring AI (`ChatClient`). Если модель не настроена
  (`spring.ai.model.chat=none`), приложение работает, а чат сообщает, что AI
  не настроен.

== Область

=== Входит

* Подключение аддона AI Tools (core, UI, хранение истории) и OpenAI-модуля
  Spring AI.
* Настройка модели `z-ai/glm-5.2` через OpenRouter в `application.properties`
  (это и есть dev-конфигурация, профилей в проекте нет), ключ — из переменной
  окружения `OPENROUTER_API_KEY`.
* Доступ к чату для сотрудника и офис-менеджера.
* Проверка, что через чат нельзя прочитать больше, чем в приложении.

=== Не входит

* *Профили Spring, прод, Docker Compose, деплой, секреты в окружении сервера* —
  урок 4.
* Действия через чат: создать, отменить, изменить бронь. Аддон из коробки
  только читает данные; свои инструменты для модели — отдельная задача.
* Свой системный промпт, RAG по документам, загрузка файлов в чат.
* Выбор модели пользователем, несколько провайдеров, учёт расходов и лимиты
  запросов к OpenRouter.
* Политика обработки персональных данных у внешнего провайдера. В dev
  используются демо-данные; для прода — урок 4.
* Изменение экранов, сущностей и ролей модулей 1–3, кроме назначения новой
  роли персонам.

== Подключение

=== Зависимости

Аддон добавляется через Studio (Add-ons → AI Tools), как другие стандартные
артефакты Jmix: Studio прописывает стартеры в `build.gradle` и подключает
changelog аддона к мастер-changelog. Версии — из Jmix BOM.

* `io.jmix.aitools:jmix-aitools-starter`
* `io.jmix.aitools:jmix-aitools-flowui-starter`
* `io.jmix.aitools:jmix-aitools-flowui-data-starter`
* changelog `/io/jmix/aitoolsflowuidata/liquibase/changelog.xml` в
  `liquibase/changelog.xml`

Модель OpenAI-совместимого API в аддон не входит. Дописывается вручную:

* `org.springframework.ai:spring-ai-starter-model-openai` — версия из
  `spring-ai-bom` 2.0.0, который импортирует Jmix BOM.

=== Настройки

OpenRouter совместим с OpenAI API, поэтому используется OpenAI-модуль
Spring AI с другим адресом.

[cols="2,3,3"]
|===
| Файл | Свойство | Значение

| `application.properties`
| `spring.ai.model.chat`
| `openai`

|
| `spring.ai.openai.base-url`
| `https://openrouter.ai/api/v1`

|
| `spring.ai.openai.api-key`
| `${OPENROUTER_API_KEY:}`

|
| `spring.ai.openai.chat.options.model`
| `z-ai/glm-5.2`

| `application-test.properties`
| `spring.ai.model.chat`
| `none` — тесты не ходят в сеть
|===

* *Адрес с `/v1`.* OpenAI-модуль Spring AI 2.0 построен на официальном
  `openai-java` SDK; адрес OpenAI по умолчанию у него —
  `https://api.openai.com/v1`, поэтому для OpenRouter тоже с `/v1`. При
  реализации проверить первым запросом.
* *Имя свойства модели.* В метаданных Spring AI 2.0 есть и
  `spring.ai.openai.chat.options.model`, и `spring.ai.openai.chat.model`. При
  реализации оставить то, которое реально применяется (проверка — модель в
  логе запроса или в ответе OpenRouter).
* *Ключ* нигде не хранится в файлах проекта: только переменная окружения.
  В git попадает лишь ссылка `${OPENROUTER_API_KEY:}`.
* *Без ключа* приложение стартует: пустой ключ, чат сообщает об ошибке
  настройки.

== Доступ

Роль аддона `aitools-chat-user` назначается обеим персонам. Свои роли модуля 2
не меняются.

[cols="2,3"]
|===
| Персона | Роли

| Сотрудник
| `ui-minimal`, `employee`, `own-bookings`, `aitools-chat-user`

| Офис-менеджер
| `ui-minimal`, `office-manager`, `aitools-chat-user`

| Администратор
| `system-full-access` — чат доступен и так
|===

Таблица назначений в `02_security/01-roles.spec.adoc` дополняется ссылкой на
эту спеку.

=== Что модель видит от имени пользователя

Модель знает только то, что вернут запросы, выполненные с правами
пользователя. Ожидаемое поведение:

* *Сотрудник* через чат получает только свои брони (row-level `own-bookings`
  на `Booking`), только себя из пользователей (row-level на `User`),
  справочники — целиком.
* *Офис-менеджер* — все брони, справочники, пользователей без `email`
  (атрибутная политика: колонка выкидывается).
* *Системные атрибуты* (`password` и др. с `@SystemLevel`) модели не
  описываются вовсе (`jmix.aitools.dataload.exclude-system-level-attributes`,
  по умолчанию `true`).

*Главный риск.* Модель пишет JPQL сама, а JPQL row-level политика гарантирует
фильтр для корневой сущности запроса. Неочевидно, действует ли она на
`Booking`, если брони достаются через соединение или подзапрос из другой
сущности (`select b.startAt, b.user.username from Room r, Booking b where
b.room = r`) или в агрегатах (`count`). Это проверяется тестами ниже. Если
тест покажет утечку — реализация останавливается и вопрос выносится к
пользователю (варианты: исключить `Booking` и `User` из модели для чата
`jmix.aitools.dataload.exclude-entities`, свой `AvailableEntityFilter` по ролям
пользователя, своя проверка запросов).

== Тесты

Без сети и без модели: вызывается сервис аддона, который выполняет готовый
JPQL (`JpqlExecutionService`), под реальными пользователями с ролями, как в
`RolesTest`. Это тот же путь, по которому идут запросы модели.

*Сотрудник:*

. `select b.id from Booking b` — только свои брони.
. `select count(b) from Booking b` — число своих броней.
. Брони через соединение: `select b.id from Room r, Booking b where b.room = r`
  и `select b.id from Room r join Booking b on b.room = r` — только свои.
. Брони через подзапрос или путь от пользователя
  (`select u.username from User u where exists (...)`) — ничего чужого.
. `select u.username from User u` — только он сам.
. `select r.name from Room r` — все переговорки.

*Офис-менеджер:*

. `select b.id from Booking b` — все брони.
. `select u.username, u.email from User u` — `email` в результате нет.

*Общее:*

. Контекст поднимается с `spring.ai.model.chat=none` (Gate 2 это и
  проверяет).

Ответы самой модели — в браузере (Gate 3): они недетерминированы и требуют
сети и ключа.

== Критерии приёмки

. Аддон подключён через Studio, changelog аддона применяется, таблицы истории
  чатов созданы.
. При заданной `OPENROUTER_API_KEY` чат отвечает моделью `z-ai/glm-5.2` через
  OpenRouter.
. Без `OPENROUTER_API_KEY` приложение стартует, чат сообщает об ошибке.
. Ключа нет ни в одном файле репозитория.
. Сотрудник и офис-менеджер видят пункт меню чата и могут общаться; у каждого
  своя история чатов.
. Сотрудник не получает через чат ни одной чужой брони и ни одного чужого
  пользователя; офис-менеджер не получает `email` пользователей. Это
  доказывают тесты раздела «Тесты».
. Тесты не обращаются к сети.
. Профили, прод-настройки, Docker Compose и деплой не тронуты.
. Gate 1 и Gate 2 зелёные; Gate 3 — пользователь прошёл чек-лист.

== Принятые решения

. *Аддон подключает пользователь* через Studio (Add-ons → AI Tools): стартеры
  и changelog аддона. Модуль `spring-ai-starter-model-openai` и настройки
  модели добавляет Claude.
. *Без ключа приложение стартует*: `${OPENROUTER_API_KEY:}`, чат сообщает об
  ошибке.
. *Профили не вводятся.* Настройки модели — в `application.properties`;
  разделение dev и прод — урок 4.
. *Утечка через соединения и подзапросы известна и пока не закрывается.*
  `AiDataAccessTest` подтвердил: row-level фильтр `own-bookings` на `Booking`
  не действует, если бронь — не корневая сущность запроса
  (`from Room r, Booking b ...`, `exists (select b from Booking b ...)`).
  Пользователь решил ничего не исключать из модели для чата. Два теста на
  утечку (`employeeReadsOnlyOwnBookingsThroughJoins`,
  `employeeCannotDetectOthersBookingsThroughSubquery`) остаются красными как
  напоминание. Варианты закрытия — в бэклоге: исключить `Booking`, `User`
  (`jmix.aitools.dataload.exclude-entities`), свой `JpqlResultValidator`, свой
  инструмент «мои брони».

== Заметки реализации

* *Ключ и модель проверены напрямую* (2026-10-09): `OPENROUTER_API_KEY` задан в
  `~/.bashrc`, ключ принимается OpenRouter; запрос к
  `https://openrouter.ai/api/v1/chat/completions` с моделью `z-ai/glm-5.2`
  вернул ответ (провайдер Together).
* *`z-ai/glm-5.2` — рассуждающая модель.* Часть токенов ответа уходит на
  рассуждение: при `max_tokens=200` текст ответа был пустым
  (`finish_reason=length`), при 2000 — нормальный ответ. В настройках лимит
  токенов не задаём.
